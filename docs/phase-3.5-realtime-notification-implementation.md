# Phase 3.5 real-time notification implementation

## Infrastructure audit

BragRight already had an authenticated, server-derived Action Center at `/api/dashboard/action-center`. Its items are generated from current match state and current-user permissions, so resolved actions disappear when the authoritative workflow changes. It also had match activity logs, shared cards, badges, buttons, skeletons, protected routes, and token refresh handling.

The project did not have persisted notification records, server-side unread state, notification preferences, a service worker, PWA push subscriptions, WebSockets, Socket.IO, SSE, a message queue, an event emitter, scheduled reminders, or sound assets. Informational Action Center items have no pagination, and there is no backend event cursor for missed-event replay. Render's current Flask/Gunicorn and static-site configuration does not include a pub/sub or push-delivery worker.

## Architecture decision

Phase 3.5 reuses the existing Action Center as the authoritative source. A single browser-tab leader performs controlled polling:

- every 60 seconds while the application is visible;
- every 5 minutes while hidden;
- immediately after focus or reconnection;
- never with overlapping requests;
- one leader per browser profile, with `BroadcastChannel` snapshots for other tabs;
- a bounded 50-item client list and maximum three visible heads-up alerts.

This is near-real-time controlled polling, not fake WebSocket delivery. It is intentionally conservative because the current production stack has no durable event stream. True instantaneous delivery and background push require the infrastructure listed below.

## Event registry and priorities

The centralized registry supports only event types already generated by `create_match_action_items`:

| Event | Category | Priority | Unresolved action | Sound eligible |
|---|---|---|---|---|
| `match_request` | match | action required | yes | yes |
| `result_awaiting_confirmation` | result | action required | yes | yes |
| `dispute_requiring_review` | dispute | action required | yes, administrator only | yes |
| `dispute_status` | dispute | important | no; player is waiting for review | no |
| `match_resolved` | result | important | no | no |
| `match_cancelled` | match | informational | no | no |

There are no urgent events because the backend supplies no authoritative deadlines. Ranking, verification, reminders, evidence deadlines, and unsupported lifecycle events are not fabricated.

## State and behavior

- Unread state is device-local and independent from unresolved workflow state.
- Unresolved counts come only from current server state and supported action-required types.
- Read and seen identifiers are account-namespaced, bounded, and synchronized across tabs.
- Deduplication uses event type plus authoritative match identifier.
- Heads-up dismissal does not resolve an action.
- Opening an action refetches the Action Center; stale unresolved actions are removed instead of being executed.
- Notification actions navigate to the existing protected Match Center or admin dispute flow. Existing match APIs remain the only way to accept, decline, confirm, or dispute.
- Deep links are allowlisted and external or malformed destinations fall back safely.
- Offline mode pauses polling and reconnect performs missed-state recovery without replaying every alert.

## Sound and browser alerts

Sound is disabled by default and can only be enabled by a user gesture. It uses a short Web Audio two-tone alert generated locally, so no copyrighted or repeatedly loaded asset is introduced. Action sounds are rate-limited to once per eight seconds, never loop, and only the active leader tab plays them. The strong setting uses the maximum application gain chosen for clarity without clipping.

Phone hardware volume, silent mode, Focus/Do Not Disturb, browser autoplay rules, and operating-system policies remain authoritative. A website cannot force a phone speaker to maximum volume or bypass silent mode.

The optional browser alert uses the Notification API only after a contextual permission request and only while the BragRight page is still open. In-app heads-up alerts remain the fallback. This is not background Web Push.

## Security and privacy

- The authenticated server derives recipients from the current user; the frontend never supplies a recipient id.
- Only existing protected destinations are accepted.
- No match mutation is performed directly from cached notification state.
- No tokens, push keys, evidence, dispute notes, or private user data are stored in notification preferences.
- Player dispute status is not incorrectly presented as an action when only an administrator can resolve it.

## Production infrastructure still required for true real time and background push

1. A persisted notification collection with recipient, event key, state version, read/resolved timestamps, expiry, and a unique deduplication index.
2. Transaction-safe notification creation after authoritative match mutations.
3. An authenticated SSE/WebSocket gateway or managed real-time provider with per-user channels and a durable replay cursor.
4. A service worker, VAPID keys, authenticated push-subscription endpoints, subscription ownership validation, and a delivery worker/queue.
5. Server-side preferences and paginated notification-history APIs.
6. A production scheduler before match or evidence deadline reminders can be supported.
7. Shared pub/sub if multiple Gunicorn instances deliver live events.
8. Delivery, deduplication, stale-action, and push-failure metrics.

No database migration, backend API contract, business workflow, ranking calculation, or deployment configuration was changed in this implementation.
